# Personal baselines

Feature 8 compares pulse, respiration and HRV with your own earlier recordings. In **Timeline**, select a point or period, choose **Baseline context**, then **Compare baseline**. Choose Coding, Studying, Reading, Meeting, Break or Other; alternatively choose a time of day in the timeline's display timezone. Each metric reports its historical baseline, accepted current reading count, signed difference and percentage, historical sample count, local dates and evidence confidence. Empty or low-quality metrics remain absent.

## Historical evidence

The historical interval is `[selected start − 30 × 24 hours, selected start)`. The current interval is `[selected start, selected end)`. Current observations never contribute to their own reference, and live, mock and demo-seed history never mix. The API supports an explicit 1–30 day lookback and a current range up to 26 hours. Thirty days means elapsed time, not thirty local calendar boundaries.

Both intervals use the selected context. Activity comparisons prioritize the manual activity recorded on each measurement. For an unlabeled measurement, exactly one overlapping context interval from the same owner/source may supply its manual activity; otherwise a non-idle classification with confidence at least 0.8 may supply activity. Unknown, low-confidence or overlapping desktop contexts are excluded. Later choices never relabel measurements. Time-of-day comparisons require no activity label: night is 00:00–06:00, morning 06:00–12:00, afternoon 12:00–18:00 and evening 18:00–24:00, with half-open local hour boundaries and date-aware DST conversion.

Accepted observations require good/excellent signal, no talking, and per-metric confidence of at least 0.4 pulse, 0.45 respiration or 0.5 HRV. Missing values and low confidence never become zero. Each historical sample is one sensing session's UTC-aligned 30-second bucket mean, with at least 15 accepted observations of that metric. Bucket means have equal weight; current means weight accepted raw readings equally. Overlapping sensing sessions remain separate samples. These samples can be correlated and are not described as independent observations.

A metric needs **20 qualifying historical samples across at least 3 local dates** before a baseline is exposed. These conservative product thresholds describe evidence support, not medical significance. A shorter lookback or context may be insufficient even when other history exists. The UI reports **Insufficient history** and actual sample/date counts. With sufficient history but no current contextual observations, it reports **No accepted readings** and retains the historical baseline.

The baseline is the mean of qualifying bucket means. `differenceAbsolute` is the signed current-minus-baseline value; `differencePercent` divides that value by baseline and multiplies by 100. A zero baseline has no percentage. `deviation` is the difference divided by the population standard deviation of historical bucket means; absent or constant history has no standardized deviation. This is descriptive, not an alert threshold or clinical interpretation.

Evidence confidence is `min(samples/100, 1) × min(localDates/7, 1) × mean historical measurement confidence`, using equally weighted bucket confidence averages. Insufficient history returns confidence zero. This documented heuristic is not a calibrated probability, confidence interval, diagnostic score or proof of stress.

The spec's first-ten-minutes-of-focus example needs a reliable focus-session start. Existing context has an observed focus boolean, which can begin midway through a session. This feature therefore exposes activity and time-of-day baselines; it does not claim that a sensing or desktop session began a focus session. Dedicated focus-session lifecycle remains part of Feature 15.

## Contracts and privacy

Pure functions in `@trueiris/analytics` expose `getActivityBaseline`, `getTimeOfDayBaseline`, `compareAgainstBaseline` and `getBaselineDeviation`. They consume scoped per-metric evidence; the database computes that evidence from raw history to preserve context and quality boundaries. No migration, baseline cache, new capture or seeded history is added. Deleting saved data removes the source of future comparisons.

Authenticated `POST /baselines/compare` accepts only `{ range: { start, end, source }, context: { kind: 'activity', activity } | { kind: 'time_of_day', period }, timezone, lookbackDays }`. The API binds all reads to its configured identity, rejects arbitrary owner IDs and unknown fields, and returns three metric comparisons plus echoed query and explicit historical bounds. A single parameterized SQL statement provides a consistent database snapshot, with the existing 5-second statement timeout and bounded time range. Context lookup may be expensive for dense history; timeout yields the visible unavailable state rather than a partial baseline. [PostgreSQL date/time functions](https://www.postgresql.org/docs/current/functions-datetime.html) provide `date_bin` and timezone conversion; [aggregate functions](https://www.postgresql.org/docs/current/functions-aggregate.html) provide population variance.

The named `getBaselines` desktop bridge validates IPC input/output. Main owns credentials, refuses redirects and insecure remote transport, bounds requests to 10 seconds, validates exact context/source/period/history boundaries, and hides private transport/SQL errors. The renderer holds results only in memory. Changing context, range, source, timezone or refreshing history clears results and prevents stale responses from replacing current selections. Comparison requires a user click and does not activate any capture.

## Validation

Unit tests cover arithmetic, signed differences, confidence/support boundaries, absent metrics, zero baselines, constant variance, strict inputs and private response validation. API tests cover authentication, owner scoping, invalid lookbacks/timezones and sanitized failure states. Built desktop tests cover selection → comparison, numeric evidence, changing context and insufficient history. `pnpm test:database` uses isolated random owners to verify real SQL aggregation, manual/inferred context, quality gates, missing/zero metrics, source and owner isolation, history cutoff/lookback, local time across DST and deletion. It cleans only those fixture owners. Run `pnpm check`, `pnpm test:integration`, `pnpm test:database` and `pnpm test:persistence` after building.
